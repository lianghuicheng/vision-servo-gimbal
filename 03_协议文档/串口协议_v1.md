## 1. 物理层约定

| 项目 | 约定 | 备注 |
|---|---|---|
| 接口 | UART，TTL 电平（3.3V） | **必须共地** |
| 波特率 | 115200 | 双方一致，不要一个 9600 一个 115200 |
| 数据位/停止位/校验 | 8 / 1 / None | 最常用 |
| 线序 | 视觉端 TX → 主控 RX；视觉端 RX → 主控 TX；GND ↔ GND | **TX/RX 要交叉** |
| 供电 | 各自独立供电，只共地 | 避免舵机/电机电流倒灌 |

> ⚠️ 常见坑：只接了 TX/RX 忘了共地 → 收到乱码。
> ⚠️ 常见坑：TLL 5V 设备直连 3.3V 主控 → 烧引脚。用逻辑分析仪或万用表先量电平。

## 2. 帧结构

```
┌────────┬────────┬───────────┬──────────────┬───────────────┬────────┐
│ 0xAA   │ 0x55   │  LEN      │   PAYLOAD    │     CRC16     │ 0x0D   │ 0x0A
│ 1 字节 │ 1 字节 │  1 字节   │   LEN 字节   │    2 字节     │ 1 字节 │ 1 字节
└────────┴────────┴───────────┴──────────────┴───────────────┴────────┘
  帧头（固定）        载荷长度        载荷内容      CRC 校验（小端）    帧尾（固定）
```

| 字段 | 长度 | 说明 |
|---|---|---|
| 帧头 | 2 B | 固定 `0xAA 0x55` |
| LEN | 1 B | PAYLOAD 的字节数，范围 1–64 |
| PAYLOAD | LEN B | 见第 3 节 |
| CRC16 | 2 B | **小端**发送（低字节在前） |
| 帧尾 | 2 B | 固定 `0x0D 0x0A` |

### CRC 算法（必须完全一致）

- 算法：**CRC-16/CCITT-FALSE**
- 参数：多项式 `poly = 0x1021`，初值 `init = 0xFFFF`，输入不反转，输出不反转，结果不异或（`xorout = 0x0000`）
- **校验范围：`LEN + PAYLOAD`**（不含帧头、CRC 本身、帧尾）
- 标准自测向量：对 ASCII `"123456789"` 计算结果必须是 **`0x29B1`**
  → 双方各自跑一遍这个测试，结果一样才能联调

> ⚠️ **极易搞混的地方**：`0x31C3` 是 **CRC-16/XMODEM** 的校验值，它的初值是 `0x0000`。
> 本协议用的是 **init = 0xFFFF**，所以校验值是 `0x29B1`。
> 我和队友如果一个人用 0x0000、一个人用 0xFFFF，就会"每一帧 CRC 都错"却怎么也查不出来。
> **联调第一步就是各自打印 `"123456789"` 的 CRC 值，对上了再往下做。**

### 为什么要有长度 + CRC + 帧尾三重校验

| 机制 | 解决什么问题 |
|---|---|
| 帧头 | 从字节流里找到帧的起点 |
| LEN | 解决**粘包/断包**（一次 read 可能收到半个帧或两个半帧） |
| CRC | 检出传输错误（电机噪声下很容易翻位） |
| 帧尾 | 二次确认，且便于人工用串口助手肉眼识别 |

## 3. PAYLOAD 定义

所有多字节字段均为**小端**。

### 3.1 `0x01` TARGET —— 检测到目标

| 偏移 | 字段 | 类型 | 说明 |
|---|---|---|---|
| 0 | type | uint8 | 固定 `0x01` |
| 1 | cx | uint16 | 目标中心 x 像素坐标 |
| 3 | cy | uint16 | 目标中心 y 像素坐标 |
| 5 | w | uint16 | 最小外接矩形宽（像素） |
| 7 | h | uint16 | 最小外接矩形高（像素） |
| 9 | angle | int16 | 目标角度，**单位 0.1°**，例：123 表示 12.3° |

**LEN = 11**

### 3.2 `0x02` LOST —— 目标丢失

结构同 TARGET，所有字段填 0（type 字段为 `0x02`）。**LEN = 11**

> 为什么要发丢失帧而不是干脆不发？——主控靠它做兜底动作（停车/报警/回到搜索位）。
> **不发帧 = 主控不知道你是"没目标"还是"线断了"。**

### 3.3 `0x03` HEARTBEAT —— 心跳

只有 type 一个字节。**LEN = 1**，每 500 ms 发一次。

> 主控据此判断视觉端是否死机：超过 1 s 没收到任何帧 → 执行安全动作。

## 4. 通信时序与容错约定

| 场景 | 约定 |
|---|---|
| 发送频率 | 视觉端 30 fps → 每帧都发（约 30 帧/秒，115200 bps 足够） |
| 无目标时 | 发 `0x02 LOST`，频率不变 |
| 主控超时判定 | 连续 1 s 未收到任何合法帧 → 视为视觉端离线 → 执行安全动作 |
| 主控回传 | v1 阶段**主控不回传**；v2 再加状态帧（见第 6 节） |
| 错误帧处理 | 收到 CRC 错误 → 静默丢弃，不回复，不崩溃 |
| 上电顺序 | 无要求，双方都需容忍对方晚启动 |

## 5. 示例帧（可直接用于自测）

以下均为**完整帧的十六进制**，可用串口助手直接发送验证。

### 5.1 TARGET：cx=120, cy=80, w=45, h=60, angle=12.3°

```
AA 55 0B 01 78 00 50 00 2D 00 3C 00 7B 00 <CRC_L> <CRC_H> 0D 0A
```

### 5.2 LOST

```
AA 55 0B 02 00 00 00 00 00 00 00 00 00 00 <CRC_L> <CRC_H> 0D 0A
```

### 5.3 HEARTBEAT

```
AA 55 01 03 <CRC_L> <CRC_H> 0D 0A
```

> Python 端可用 `protocol.py` 生成实际字节：
> ```python
> from protocol import pack_target, pack_lost, pack_heartbeat
> print(pack_target(120, 80, 45, 60, 12.3).hex(' '))
> print(pack_lost().hex(' '))
> print(pack_heartbeat().hex(' '))
> ```

## 7. 联调检查清单（按顺序做，不要跳）

- [ ] 双方各自跑通 CRC 自测向量 `0x29B1`（对 `"123456789"`，init=0xFFFF）
- [ ] 先只发**心跳帧**，主控能正确解析出 type=0x03
- [ ] 再发**固定内容的 TARGET 帧**，主控打印出的 5 个数值与预期完全一致
- [ ] 在 XCOM 里**故意删掉几个字节**再发，主控应丢弃而不是打印乱值
- [ ] 在 XCOM 里**故意改掉 CRC 两个字节**，主控应计入 CRC 错误
- [ ] 连发 1000 帧，主控接收计数 ≥ 999（115200 下应几乎不丢）
- [ ] 接上电机，**边转电机边传数据**，观察误帧率是否上升（这是 W13 电源问题的前哨）
- [ ] 拔掉视觉端电源，1 s 内主控应进入安全动作
